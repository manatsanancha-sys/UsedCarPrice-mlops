# AI Project Canvas — ระบบทำนายราคารถมือสอง (ร่างเนื้อหา)

> ร่างเนื้อหาสำหรับนำไปจัดหน้าใน Canva ตัวเลขทั้งหมดมาจากโมเดล Ridge ที่เป็น `champion` ล่าสุดใน MLflow Registry
> รันบน `data/processed/val.csv` และ `test.csv` เว้นแต่ติดป้ายไว้ดังนี้
> - **[ค่าปัจจุบันวัดจริง, เป้าหมายเป็นข้อเสนอของทีม]** — ตัวเลขปัจจุบันมาจากผลทดสอบจริง ส่วนเป้าหมาย/KPI ทีมตั้งขึ้น
> - **[สมมติฐาน]** — ไม่มีข้อมูลรองรับโดยตรง เป็นการประเมินของทีม
> - **[แนวคิดสำหรับต่อยอด — ไม่ได้วัดในโปรเจกต์นี้]** — อยู่นอกขอบเขตโปรเจกต์ เสนอไว้สำหรับพัฒนาต่อ
> อัตราแลกเปลี่ยนที่ใช้: 1 INR = 0.39 THB (ค่าเดียวกับ `INR_TO_THB` ใน `src/api.py`)

---

## 1. Value Proposition (คุณค่าที่ระบบสร้าง)
- ผู้ขายรถมือสองรายย่อยได้ **ราคาอ้างอิงทันที** จากสเปกรถ (ยี่ห้อ/รุ่น ปี เลขไมล์ เชื้อเพลิง เกียร์ ฯลฯ) โดยไม่ต้องไล่เทียบประกาศเองหรือจ้างผู้ประเมิน
- ลดความเสี่ยง 2 ด้าน: ตั้งราคา **ต่ำเกินไป** (ขาดทุน) และ **สูงเกินไป** (ขายไม่ออก ประกาศค้างนาน)
- แพลตฟอร์มประกาศขายรถได้ราคาแนะนำที่สม่ำเสมอ ช่วยให้ผู้ซื้อเชื่อใจราคาในตลาดมากขึ้น

## 2. Customers / Users
| กลุ่ม | ใช้ระบบอย่างไร |
|---|---|
| ผู้ขายรายบุคคล (Individual) — ผู้ใช้หลัก | กรอกข้อมูลรถตอนลงประกาศ แล้วได้ราคาแนะนำทันที |
| ดีลเลอร์ (Dealer / Trustmark Dealer) | ใช้ประเมินราคารับซื้อ/ตั้งราคาขายต่อ |
| ผู้ซื้อ | ใช้ตรวจว่าราคาประกาศสมเหตุสมผลหรือไม่ |

## 3. Stakeholders
- **เจ้าของแพลตฟอร์ม / ทีมธุรกิจ** — ต้องการให้ประกาศขายได้เร็วขึ้นและผู้ใช้กลับมาใช้ซ้ำ
- **ทีม ML / MLOps (กลุ่มเรา)** — ดูแลโมเดล การเฝ้าระวัง และการเทรนใหม่
- **ทีมให้บริการลูกค้า** — รับเรื่องเมื่อราคาแนะนำผิดมาก
- **ผู้สอน / ผู้ตรวจ** — ประเมินว่าระบบทำงานได้จริงตั้งแต่ต้นจนจบ

## 4. ML Task และเหตุผลที่ใช้ ML แทนการเขียนกฎ
- **งาน:** Regression — ทำนาย `selling_price` (รูปี) จาก 12 features
  (`year, km_driven, mileage, engine, max_power, torque, seats, brand, fuel, seller_type, transmission, owner`)
- **ทำไมกฎธรรมดาไม่พอ:**
  - ราคาขึ้นกับหลายปัจจัยพร้อมกันแบบไม่เป็นเส้นตรง (เช่น ค่าเสื่อมต่อปีของแต่ละยี่ห้อไม่เท่ากัน, เลขไมล์มีผลต่างกันตามอายุรถ)
  - มี 30+ ยี่ห้อ × เชื้อเพลิง × เกียร์ × จำนวนเจ้าของ — จำนวนกฎที่ต้องเขียนเองระเบิด และต้องแก้มือทุกครั้งที่ตลาดเปลี่ยน
  - baseline แบบ "ใช้ราคากลาง (median) ของตลาด" ซึ่งเทียบเท่ากฎง่ายที่สุด ได้ val MAPE **45.3%** ขณะที่ Ridge ได้ **17.1%**
  - ML เทรนใหม่จากข้อมูลล่าสุดได้อัตโนมัติเมื่อตลาดเปลี่ยน (ดูหัวข้อ Drift)

## 5. Data
- **แหล่งข้อมูล:** Vehicle Dataset from CarDekho (Kaggle, `nehalbirla/vehicle-dataset-from-cardekho`, ไฟล์ `Car details v3.csv`) ดาวน์โหลดด้วย `scripts/download_data.py`
- **ขนาด:** 8,128 แถว → **6,926 แถว** หลังลบข้อมูลซ้ำ 1,202 แถว (ผ่านเกณฑ์แนะนำ ≥ 5,000)
- **การแบ่งชุดข้อมูล (ตามปีรถ เพื่อเลียนแบบการใช้งานในอนาคต):**
  | ชุด | เงื่อนไข | จำนวน |
  |---|---|---|
  | train | ปี ≤ 2016 | 5,100 |
  | val | ปี = 2017 | 808 |
  | test | ปี ≥ 2018 | 1,018 |
- **การตรวจคุณภาพ:** Pandera schema (`src/validation.py`) — ช่วงค่า, ค่าหมวดหมู่ที่อนุญาต, ห้ามมีคอลัมน์แปลกปลอม
- **ข้อจำกัด:** ข้อมูลอินเดีย (ราคาเป็นรูปี), ข้อมูลสิ้นสุดที่ปี 2020, ไม่มีข้อมูลสภาพรถ/อุบัติเหตุ

## 6. Output และ Integration
- **Output:** `predicted_price_inr` และ `predicted_price_thb` + `model_version`
- **Integration:** REST API (`POST /predict`) แบบ real-time ใน Docker container — เรียกจากหน้าลงประกาศได้ทันที
- ข้อมูลผิดรูปแบบ (เช่น `fuel="Water"`, ปี 2099, เลขไมล์ติดลบ) ถูกปฏิเสธด้วย HTTP 422 ไม่คืนราคามั่ว

## 7. Metrics

### Optimizing metric: **MAE** (Mean Absolute Error, หน่วยรูปี)
- เลือกเพราะ **อ่านเป็นเงินได้ตรงๆ** ("ราคาแนะนำคลาดเฉลี่ยกี่บาท") สื่อสารกับฝ่ายธุรกิจง่าย และไม่ถูกรถราคาแพงไม่กี่คันดึงค่ามากเท่า RMSE
- ผล: val MAE **120,615 INR (~47,000 THB)**, test MAE **184,906 INR (~72,100 THB)**

### Gating metric: **MAPE ≤ 20%** บน test set
- เป็นด่านตรวจใน `src/register.py` (`GATE_MAPE = 0.20`) — ไม่ผ่านจะไม่ถูก promote เป็น `champion`
- ผลจริง: test MAPE **19.6%** → ผ่าน (แต่เหลือระยะห่างจากเกณฑ์เพียง 0.4 จุด)
- เกณฑ์ระบบ (SLO) ที่ต้องผ่านด้วย: p95 latency ≤ 250 ms, error rate ≤ 1% (ดู `docs/SLO_AND_RETRAIN_POLICY.md`)

## 8. เชื่อมตัวชี้วัดโมเดลกับตัวชี้วัดธุรกิจ

### MAE 184,906 รูปี หมายถึงอะไร
| ตัวเลข (test set, รถปี 2018–2020) | ค่า |
|---|---|
| ราคาเฉลี่ยจริง | 896,128 INR (~349,500 THB) |
| ราคากลาง (median) จริง | 695,000 INR (~271,000 THB) |
| MAE | 184,906 INR (~72,100 THB) = **20.6% ของราคาเฉลี่ย** |
| ความคลาดเคลื่อนกลาง (median absolute error) | 103,991 INR (~40,600 THB) — รถ "ทั่วไป" คลาดประมาณนี้ |

- **แปลเป็นภาษาธุรกิจ:** ถ้าผู้ขายตั้งราคาตามที่ระบบแนะนำ โดยเฉลี่ยจะคลาดจากราคาตลาดจริงราว **1 ใน 5 ของราคารถ**
  - ถ้าระบบแนะนำ **ต่ำ** กว่าจริงเกิน 20% → ผู้ขาย **เสียเงิน** (ตัวอย่าง: รถราคากลาง 695,000 INR ขาดทุนได้ถึง ~139,000 INR / ~54,000 THB)
  - ถ้าระบบแนะนำ **สูง** กว่าจริงเกิน 20% → ประกาศ **ขายช้า/ขายไม่ออก** ต้องลดราคาภายหลัง
- **สัดส่วนการทำนายบน test set:**
  | กลุ่ม | สัดส่วน |
  |---|---|
  | คลาดไม่เกิน ±10% | 33.3% |
  | คลาดไม่เกิน ±20% (ใช้งานได้ดี) | **63.2%** |
  | แนะนำต่ำกว่าจริงเกิน 20% (เสี่ยงขาดทุน) | 20.1% |
  | แนะนำสูงกว่าจริงเกิน 20% (เสี่ยงขายช้า) | 16.7% |
- **ความแม่นยำแยกตามช่วงราคา (test):**
  | ช่วงราคา (INR) | จำนวน | MAE | MAPE |
  |---|---|---|---|
  | < 300,000 | 23 | 178,373 | **70.7%** |
  | 300,000–700,000 | 489 | 93,623 | 19.2% |
  | 700,000–1,500,000 | 409 | 146,321 | **15.8%** |
  | ≥ 1,500,000 | 97 | 809,327 | 25.8% |
  → ระบบแม่นที่สุดในช่วงรถราคากลาง (ตลาดหลัก ~88% ของข้อมูล) แต่ **ไม่ควรใช้กับรถราคาต่ำมากหรือรถหรู** โดยไม่แสดงคำเตือน

### ตัวชี้วัดธุรกิจที่เสนอ **[ค่าปัจจุบันวัดจริง, เป้าหมายเป็นข้อเสนอของทีม]**
| KPI ธุรกิจ | เชื่อมกับตัวชี้วัดโมเดล | เป้าหมายที่เสนอ |
|---|---|---|
| % ประกาศที่ราคาแนะนำคลาดไม่เกิน ±20% จากราคาขายจริง | MAPE / สัดส่วน within 20% | ≥ 60% (ปัจจุบัน 63.2%) |
| ระยะเวลาเฉลี่ยจากลงประกาศถึงขายได้ | ราคาแนะนำสูงเกินจริง → ขายช้า | ลดลงเทียบกับก่อนมีระบบ (วัดด้วย A/B test) (แนวคิดสำหรับต่อยอด ไม่ได้วัดในโปรเจกต์นี้) |
| % ผู้ขายที่ใช้ราคาแนะนำ (adoption rate) | ความเชื่อมั่นในความแม่นยำ | ≥ 50% ของประกาศใหม่ (แนวคิดสำหรับต่อยอด ไม่ได้วัดในโปรเจกต์นี้) |
| จำนวนเรื่องร้องเรียนว่าราคาแนะนำผิด | error rate + ความคลาดกลุ่มรถหรู/ราคาต่ำ | ลดลงต่อเนื่องทุกเดือน (แนวคิดสำหรับต่อยอด ไม่ได้วัดในโปรเจกต์นี้) |

## 9. ถ้าโมเดลทำนายผิด ใครเดือดร้อน และอย่างไร
| ผู้ได้รับผลกระทบ | ทำนายต่ำเกินจริง | ทำนายสูงเกินจริง |
|---|---|---|
| ผู้ขาย | ขายขาดทุน (ความเสียหายที่ย้อนคืนไม่ได้ — ร้ายแรงกว่า) | ขายช้า ต้องลดราคาทีหลัง |
| ผู้ซื้อ | — (ได้ประโยชน์) | จ่ายแพงเกินจริงถ้าเชื่อราคาแนะนำ |
| แพลตฟอร์ม | เสียความเชื่อมั่นจากผู้ขาย | ประกาศค้างนาน สินค้าหมุนเวียนช้า |

- **กลุ่มเสี่ยงสูงสุด:** รถราคา < 300,000 INR (MAPE 70.7%) และรถหรู ≥ 1.5 ล้าน INR (คลาดเฉลี่ย ~809,000 INR)
- **การบรรเทา:** แสดงเป็น "ช่วงราคา" แทนตัวเลขเดียว, แสดงคำเตือนสำหรับกลุ่มราคาที่แม่นยำต่ำ, เก็บ log ทุกคำขอ (`logs/predictions.log`) เพื่อตรวจย้อนหลัง, rollback ได้ทันที (`src/rollback.py`)

## 10. Data Drift และ Concept Drift ที่คาดว่าจะเกิด (อ้างอิงผลจริง)

### Data Drift — การกระจายของ input เปลี่ยน
ผลจริงจาก `src/monitor_drift.py` (Evidently, train ปี ≤ 2016 เทียบ test ปี ≥ 2018) → `reports/drift_report.html`:
**Dataset Drift = Detected, 91.7% ของคอลัมน์ drift (11 จาก 12)**

| สิ่งที่เปลี่ยน | train | test |
|---|---|---|
| เลขไมล์กลาง (`km_driven`) | 80,000 km | 23,150 km |
| สัดส่วนเกียร์อัตโนมัติ | 5.9% | 18.7% |
| สัดส่วนเชื้อเพลิง Diesel / Petrol | 56.6% / 42.0% | 42.9% / 55.7% |
| ราคากลาง | 325,000 INR | 695,000 INR |

สาเหตุที่คาดในโลกจริง: รถรุ่นใหม่เข้าตลาดมือสอง, ผู้บริโภคหันไปใช้เกียร์อัตโนมัติ/เบนซิน, ยี่ห้อและรุ่นใหม่ที่โมเดลไม่เคยเห็น, นโยบายภาครัฐเรื่องรถดีเซล

### Concept Drift — ความสัมพันธ์ระหว่าง feature กับราคาเปลี่ยน
ผลจริงจาก `src/monitor_concept_drift.py`: MAE ของ test / MAE ของ val = **1.53** เกินเกณฑ์ **1.3** → **Concept Drift = Detected**

สาเหตุที่คาดในโลกจริง: เงินเฟ้อและราคารถใหม่ขึ้น (รถสเปกเดิมราคาสูงขึ้น), ภาษี/กฎหมายการปล่อยมลพิษ, ช่วงขาดแคลนชิป (รถมือสองราคาพุ่ง), ค่าเสื่อมของยี่ห้อที่เปลี่ยนตามภาพลักษณ์แบรนด์

### การตอบสนอง
ตามนโยบายใน `docs/SLO_AND_RETRAIN_POLICY.md`: drift เกินเกณฑ์ → เทรนใหม่ → ต้องผ่าน gate MAPE ≤ 20% → promote เป็น champion ใหม่ ถ้าแย่กว่า → rollback

## 11. Cost **[สมมติฐาน]**
**มีตัวเลขจริงรองรับ** (ผล load test ใน `docs/SLO_AND_RETRAIN_POLICY.md`)
- โครงสร้างพื้นฐาน: container ขนาดเล็ก 1 ตัว (Ridge inference < 50 ms, รองรับ ~200 req/s บน 4 workers)

**การประเมินเชิงคุณภาพ** (ไม่มีตัวเลขรองรับ)
- ค่าโครงสร้างพื้นฐานโดยรวม: คาดว่าต่ำ เพราะใช้ container เดียวก็รองรับโหลดได้เกินความต้องการ
- ข้อมูล: ใช้ข้อมูลสาธารณะ ไม่มีค่าใช้จ่าย แต่ในระบบจริงต้องเก็บราคาขายจริงจากประกาศเพื่อเทรนใหม่
- บุคลากร: เวลาของทีมในการเฝ้าระวังและเทรนใหม่รายเดือน

## 12. Revenue / Benefit **[แนวคิดสำหรับต่อยอด — ไม่ได้วัดในโปรเจกต์นี้]**
- เพิ่มจำนวนประกาศที่ขายสำเร็จและลดเวลาขาย → ค่าธรรมเนียมแพลตฟอร์มเพิ่มขึ้น
- ใช้เป็นฟีเจอร์ premium สำหรับดีลเลอร์ (ประเมินราคาจำนวนมาก)
- ลดต้นทุนทีมบริการลูกค้าจากเรื่องร้องเรียนเรื่องราคา
